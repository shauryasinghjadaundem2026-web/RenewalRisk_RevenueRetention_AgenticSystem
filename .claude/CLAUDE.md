# CLAUDE.md

Guidance for an AI coding assistant (or a future contributor) picking this
repository up. See `README.md` for how to run things and
`ARCHITECTURE.md` for the full design write-up — this file is about repo
conventions and where things live.

## What this repo is

A multi-agent, human-in-the-loop renewal-risk and retention system for a
B2B SaaS book of business. It is deliberately built as plain, readable
Python modules called in sequence by an orchestrator — not a heavier agent
framework — so the whole reasoning chain stays inspectable and replayable.
"Agent = Model + Harness": the model is the trained risk classifier and its
counterfactual simulation; the harness is everything else (the pipeline,
tool calls, RAG, guardrails, Claude Skills, audit log).

## Repo map

```
agents/
  data_pipeline.py   - Signal Ingestion: joins the 5 raw tables into one account table
  risk_model.py       - Risk Scoring: trains/scores the logistic regression model
  roi_engine.py        - Reasoning & ROI: builds and ranks retention options
  policy_rag.py         - Policy Agent: TF-IDF retrieval over the playbook
  orchestrator.py        - Decision Router + Audit: ties everything together, writes output/
policy/retention_playbook.md   - the guardrail policy (7 clauses), read by policy_rag.py
data/*.xlsx                     - raw RavenStack dataset, read by data_pipeline.py
output/                          - regenerated by orchestrator.py (full detail + audit log)
dashboard-data.json               - snapshot of output/dashboard_data_full.json, read by the dashboards
dashboard.html                     - dashboard UI (incl. the Agent console tab), loads dashboard-data.json via fetch()
index.html                          - same UI with dashboard-data.json embedded inline (no server needed)
tools/build_dashboard_data.py        - derives dashboard-data.json from output/dashboard_data_full.json
tools/build_index.py                 - regenerates index.html from dashboard.html + dashboard-data.json
skills/                                - Claude Skills, human-browsable copy: the reasoning patterns behind agents/
.claude/skills/                          - identical copy of skills/, at the path Claude Code actually auto-loads from
```

`skills/` and `.claude/skills/` must be kept byte-identical. `.claude/`
is a dotfolder — it's invisible in Finder/Explorer by default and in some
zip viewers, which is exactly why `skills/` exists as a second, plainly
visible copy. If you edit a SKILL.md, copy the change into both paths.

## Claude Skills — load these before touching the corresponding agent

`.claude/skills/` holds five skills that document *why* each agent's
approach is built the way it is, not just what the code does. If you're
picking this repo up in Claude Code, these trigger automatically; if
you're a human contributor (or another assistant without skill-loading),
read the relevant one before changing the matching file:

| Skill | Read before touching |
|---|---|
| `renewal-risk-feature-engineering` | `agents/data_pipeline.py`, `risk_model.py`'s feature lists |
| `risk-driver-explainability` | `risk_model.py`'s `HUMAN_LABELS` / driver extraction |
| `retention-roi-simulation` | `agents/roi_engine.py` |
| `policy-clause-grounding` | `agents/policy_rag.py`, `policy/retention_playbook.md` |
| `hitl-escalation-guardrails` | `agents/orchestrator.py`'s Decision Router, `policy/retention_playbook.md` Clauses 1–2, 6 |

If you change one of these agents in a way that contradicts its skill
(e.g. adding a leakage-prone feature, or an unlabeled assumed number),
update the skill too — they're meant to stay true to the code, not just
describe an earlier version of it.

## Conventions to preserve

- **All file paths in `agents/*.py` are relative to the repo root via
  `Path(__file__).resolve().parent.parent`** — never hardcode an absolute
  path. This is what makes the pipeline portable across machines.
- **Leakage safety is load-bearing, not a style preference.** Any field
  that is only observable because an account already churned (churn
  reason, refund, subscription end-date) must stay out of the *live*
  scoring feature set (`NUMERIC_FEATURES` / `BOOL_FEATURES` /
  `CATEGORICAL_FEATURES` in `risk_model.py`). If you add a new raw column,
  check which side of that line it falls on before wiring it in.
- **Every number is either "fitted" or "assumed", and the code says which.**
  The discount-elasticity assumption (Playbook Clause 5) is deliberately
  labelled as externally benchmarked, not fitted, everywhere it surfaces
  (README, ARCHITECTURE.md, and in the dashboard's System Design tab). If
  you replace it with a fitted figure, update the labels too, not just the
  number.
- **Policy changes belong in `policy/retention_playbook.md`, not scattered
  as magic numbers in `orchestrator.py`.** The escalation thresholds,
  discount/spend caps, and value tiers are meant to live in one place a
  non-engineer can read and approve. If you add a new guardrail, add its
  clause to the playbook first, then wire `orchestrator.py`'s routing logic
  to match — and keep the clause numbers and prose in sync with the
  citations in `README.md` / `ARCHITECTURE.md`.
- **`index.html` is a generated file — don't hand-edit it.** Edit
  `dashboard.html` (the source of truth for the UI/JS/CSS) and/or
  `dashboard-data.json` (the data), then run `python3 tools/build_index.py`
  to regenerate `index.html`. Hand-edits to `index.html` will be silently
  lost the next time someone regenerates it.
- **`dashboard-data.json` vs. `output/dashboard_data_full.json`**: the
  latter is the full pipeline output (every field, every account) written
  by `orchestrator.py`; the former is derived from it by
  `tools/build_dashboard_data.py`, which adds a few flat convenience fields
  (`action_label`, `cost`, `revenue_saved`, `net_benefit`, `roi`, derived
  from each account's recommended option) that the summary tables read
  directly — but keeps every account's full `options[]` list, policy
  clause text and routing reason intact, because the **Agent console** tab
  needs the full detail to replay any account's six-step run, not just the
  escalated ones. Don't hand-trim this file or drop fields from it — the
  console silently breaks for whichever accounts lose detail.
- **The dashboards have no backend.** `writeDecision()` in the dashboard's
  script (search for it in `dashboard.html`) currently keeps
  human-in-the-loop decisions in browser memory for that session only. If
  `window.claude.use` is available (i.e. running inside a Claude Artifact)
  it also persists to that artifact's shared database; anywhere else, it's
  local-only by design. Wiring this to a real backend is the natural next
  step for a production deployment — do it by replacing the body of
  `writeDecision()`, not by restructuring the render pipeline around it.
- **The Agent console tab** (`renderConsole()`, `runOneConsoleAccount()`,
  `runConsoleAgents()`, `runConsoleAll()`, `consoleStepCards()` in
  `dashboard.html`) replays the six-agent pipeline client-side for a
  chosen account, purely from data already in `dashboard-data.json` — it
  calls no backend and adds no new data fields. `runConsoleAgents()` runs
  one account at the normal (420ms/step) pace; `runConsoleAll()` chains
  `runOneConsoleAccount()` across every account in the currently filtered
  queue list at a much faster pace (70ms/step + a short gap) and doubles
  as its own Stop button (`runAllActive`/`runAllStop` flags) — a hard stop
  (`stopRunAllConsole()`) fires when something else interrupts it (picking
  a different account), a soft stop lets the in-flight account finish and
  print "Stopped at X of Y" first. Its decision state (`writeDecision()`)
  is shared with the Escalation queue tab *and* the Overview tab's
  "Largest accounts awaiting a decision" table: all three read/write the
  same per-account `.decision-status-slot` elements, kept in sync via
  `document.querySelectorAll(...).forEach(...)` rather than
  `querySelector`, since the same account can render in more than one
  place at once. If you add another UI surface that shows a decision
  status, follow that same `querySelectorAll` pattern or it will silently
  drift out of sync with the others.
- **The Overview tab's "Replay agent cycle"** (`runReplay()`,
  `replayOrder()`, `kpiTiles()`, `paintKpiTiles()` in `dashboard.html`) is
  a purely cosmetic, client-side animation — it does not re-run the model
  or re-derive anything the pipeline hasn't already computed. It walks a
  combined, account-number-ordered list of every escalation_queue +
  autonomous_log record in small batches, accumulating the same running
  totals `agents/orchestrator.py` computed into `macro` (ARR scored, ARR
  at risk by tier, escalation count/ARR, autonomous cost/savings/net
  benefit), and paints the KPI tiles and headline with the partial sums
  until it reaches the real, exact `DATA.macro` values at the end (so
  there's no float-drift risk from the animation itself). It auto-runs
  once ~350ms after the page loads and again any time **Replay agent
  cycle** is clicked. `money()`'s `{compact:true}` mode switches to an
  "M" suffix above $1M (added alongside this feature) — don't revert that
  to the old always-"K" behavior, large ARR figures were unreadable as
  "$11563k".

## Common tasks

- **Re-run the whole pipeline** (after changing the data or the model):
  ```bash
  pip install -r requirements.txt
  python3 agents/orchestrator.py          # 1. score accounts, route, write output/
  python3 tools/build_dashboard_data.py   # 2. build dashboard-data.json from that output
  python3 tools/build_index.py            # 3. rebuild the standalone index.html
  ```
- **Regenerate the standalone dashboard after changing only the UI**
  (`dashboard.html`) or hand-editing `dashboard-data.json`, with no pipeline
  changes: `python3 tools/build_index.py` alone (run from the repo root).
- **Swap in a different dataset**: match the five schemas
  `data_pipeline.py` expects (accounts, subscriptions, churn events,
  support tickets, feature usage) and drop the new `.xlsx` files into
  `data/`, or point `data_pipeline.py` at a different loader (e.g. a live
  CRM/billing API) — the rest of the pipeline is dataset-agnostic as long
  as the joined output has the same feature columns.
- **Add a new retention option**: extend `roi_engine.py`'s option
  generator and the cost catalogue in Playbook Clause 3, keeping the two
  in sync.

## What not to do

- Don't reintroduce a leakage field into the live scoring feature set to
  "improve" AUC — the holdout number needs to mean what it says.
- Don't hardcode a discount-elasticity number without labelling it as
  assumed vs. fitted — that transparency is the whole point of Clause 5.
- Don't move guardrail thresholds into code without also updating
  `policy/retention_playbook.md` — the playbook is meant to be the
  human-readable source of truth a non-engineer reviewer can audit.
